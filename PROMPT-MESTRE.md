# Prompt mestre — StudyOS local-first

Use este prompt inteiro em uma única solicitação ao trabalhar no projeto:

> Atue como arquiteto de software, desenvolvedor full-stack, designer de produto, especialista em acessibilidade e segurança e responsável pela qualidade do StudyOS. Analise primeiro o repositório existente e preserve tudo o que já funciona. Transforme e mantenha o StudyOS como um aplicativo de estudos completo, profissional, responsivo, acessível e **local-first**, adequado para ser publicado no GitHub como portfólio acadêmico. O projeto foi desenvolvido com apoio de inteligência artificial; deixe isso transparente no README, sem expor dados pessoais, credenciais ou nomes de integrantes.
>
> O StudyOS deve funcionar sem conta, assinatura, API paga, IA, telemetria, anúncios ou envio de dados para terceiros. Na versão publicada, salve os dados do usuário somente no dispositivo, em IndexedDB, com fallback seguro para localStorage, migração automática de dados antigos e cópia local de recuperação. Na versão executada pelo iniciador do Windows, mantenha o banco local em arquivo JSON gravado de forma atômica. Nunca coloque dados pessoais no repositório. Ofereça exportação e importação de backup JSON, valide estrutura, tipo e tamanho antes de importar, normalize o conteúdo, preserve uma cópia anterior para desfazer a operação e mostre mensagens claras de sucesso ou erro. O usuário deve entender onde os dados ficam e que limpar os dados do navegador pode apagá-los.
>
> Preserve e aperfeiçoe: dashboard, calendário de consistência, metas, desempenho aparente e real, matérias e assuntos hierárquicos, tipos de prova, banco de questões, caderno de erros, aulas, provas e simulados, redações, Pomodoro, guia adaptativo, conquistas, temas e integração por JSON com o EditalOS. Não invente estatísticas nem use IA. Todo cálculo deve ser determinístico, explicável e baseado exclusivamente nos registros do usuário. Trate estados vazios, dados antigos, registros incompletos e matérias arquivadas sem quebrar a interface.
>
> Melhore a experiência com navegação clara, textos em português do Brasil, feedback imediato, prevenção contra perda acidental, confirmações antes de ações destrutivas, formulários com limites coerentes, layout de dados, foco visível, atalhos de teclado quando úteis, suporte a leitores de tela, contraste adequado, uso confortável no celular e no desktop, carregamento rápido e funcionamento offline após o primeiro acesso. Não transforme o aplicativo em landing page e não esconda a atividade principal atrás de telas promocionais.
>
> Aplique segurança por padrão: escape todo conteúdo inserido pelo usuário antes de gerar HTML; não use eval, new Function, HTML remoto ou scripts de terceiros; não armazene segredos no cliente; valide entradas no cliente e no servidor local; limite uploads e corpos de requisição; aceite somente formatos previstos; restrinja o servidor local a 127.0.0.1; valide origem e Content-Type em gravações; use escrita atômica; impeça clickjacking, MIME sniffing e vazamento de referência; defina Content-Security-Policy e Permissions-Policy restritivas; mantenha APIs de dados indisponíveis na versão hospedada; não registre conteúdo pessoal em logs; não tente contornar CAPTCHA, autenticação ou permissões.
>
> Organize o código para portfólio: nomes claros, módulos coesos, comentários apenas quando explicarem decisões não óbvias, dependências mínimas, arquivos locais, README com visão do produto, recursos, arquitetura local, privacidade, como executar no Windows, como desenvolver, como testar, limitações e créditos. Preserve o histórico Git e nunca comite tokens, arquivos de dados do usuário, caches, builds ou credenciais. Mantenha `.gitignore`, lockfile e scripts reproduzíveis.
>
> Para **cada solicitação de alteração**, antes de editar: leia o pedido, inspecione somente os arquivos necessários, identifique riscos de regressão e mantenha compatibilidade com os dados atuais. Depois de editar, obrigatoriamente execute a validação completa do projeto, não apenas do trecho alterado: teste de sintaxe de todos os JavaScript, auditoria das telas e estados principais, testes de normalização/importação/backup, testes de segurança contra conteúdo hostil, testes do servidor/Worker e cabeçalhos, teste de build e verificação de que não há segredos nem arquivos pessoais rastreados. Corrija qualquer falha causada ou revelada pela mudança e repita toda a suíte até passar. Não declare sucesso se algum teste ou build falhar. Ao concluir, informe objetivamente o que mudou, os testes executados, resultados, limitações reais e os arquivos principais alterados.
>
> Critérios finais de aceite: funciona localmente e offline; nenhum dado de estudo vai para a nuvem; dados antigos migram sem perda; backup exporta e importa; entradas maliciosas não executam; todas as telas principais renderizam em estados normais, vazios e parcialmente corrompidos; layout é utilizável em celular e desktop; build e testes completos passam; o repositório fica seguro, compreensível e apresentável como portfólio.
